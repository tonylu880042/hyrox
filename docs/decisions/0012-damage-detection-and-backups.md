# ADR 0012 — 壞檔偵測與備份策略

**Status:** accepted, 2026-09-01
**Extends:** ADR 0002（落地才 ACK）、ADR 0009（出貨形態）

## Context

問題是使用者提的：多執行緒同時讀寫 `hyrox.db`，會不會把檔案弄壞？

查了實際設定，**併發不是風險**：

* 一個行程、一個連線池（sqlx 預設上限 10 條、`busy_timeout` 5 秒）
* WAL + `synchronous=FULL`（ADR 0009 §7），本機磁碟，沒有網路檔案系統
* 所有寫入都在同一把 `Mutex<LiveSession>` 之下——MQTT 進料、HTTP 寫入、tick 迴圈
* 兩個寫入者相撞的最壞結果是 `database is locked`，那是一個錯誤，不是毀損

那把鎖被拿住多久，2026-09-03 量過（release build）：

| 誰拿鎖 | 多久 |
| --- | --- |
| `ingest_read`（解碼＋判讀＋`synchronous=FULL` 的 COMMIT） | 457 µs |
| `/api/stages` 投影，30 人 × 8 站 | 10 µs |

讀取是它可能擋到的那個寫入的 2%，而一堂 30 人的課整場約 480 次刷卡。**單一互斥鎖不是瓶頸，
`RwLock` 也不會有幫助**——`ingest_read` 要 `&mut`，tick 迴圈也會改狀態，寫入者本來就佔絕大多數。

**真正的規則是：拿著鎖就不要碰 I/O。** 記憶體裡的計算有上限，磁碟沒有——一張隨賽季長大的表
會把等待長度接到「刷卡到 ACK」之間。`backup()` 一開始就是對的（`VACUUM INTO` 要好幾秒，
它完全不拿鎖）；`Operator::exceptions()` 一開始是錯的（拿著鎖查 `interpreted_events`，
而設定頁每 5 秒問一次），2026-09-03 修正為先取 session id、放掉 guard、再查。
回歸測試 `crates/api/tests/contention.rs` 把假 store 的那個查詢卡住，然後要求 `/api/live`
仍然要在兩秒內回應。

真正的風險有三個，而且原本**一個都沒有處理**：

1. **執行中用 `cp` 複製資料庫當備份。** 漏掉 `-wal` 就是一份壞檔，而這是最常見的做法。
2. **完全沒有備份。** 整個 repo grep 不到 `VACUUM INTO`、`.backup` 或任何備份腳本。
3. **完全沒有完整性檢查。** 便宜快閃記憶體壞掉時，主機會若無其事地繼續跑。

第三點和 ADR 0002 合起來才是真正危險的地方：我們**先落地才 ACK**，而 ACK 等於告訴 ESP32
「這筆你可以丟了」。從一個壞掉的資料庫發 ACK，等於一邊丟失資料一邊叫邊緣也把副本刪掉。

## Decision

### 1. 開機時檢查，壞了就不開

`Store::open` 在跑 migration **之前**做 `PRAGMA quick_check`。壞檔回傳
`StoreError::Damaged`，主機印出問題與還原指示，然後以 **exit code 78** 結束。

用 `quick_check` 不用 `integrity_check`：它抓得到真正要命的損壞（頁面解析不了），
但不做索引交叉比對，時間是毫秒級而不是秒級。每次開機都要跑的東西，必須便宜到沒有人想關掉它。

嚴重損壞的檔案會讓檢查本身以 SQLITE_CORRUPT(11) / SQLITE_NOTADB(26) 失敗，甚至在連線階段
就失敗——這些一律當成同一份損壞報告，呼叫端不需要分辨兩種形狀。

**為什麼是「不開」而不是「降級運行」**：主機不在，讀卡機就會把事件留在自己的 journal 裡
（CLAUDE.md 15、18）。主機半殘地跑著才是最糟的——它會繼續 ACK，邊緣就會繼續刪。

systemd 單元加了 `RestartPreventExitStatus=78`，否則 `Restart=always` 會讓機器每秒
重開進同一個壞檔，把問題藏在一個閃爍的 unit 後面。

### 2. 備份由主機自己做，用 `VACUUM INTO`

`POST /api/operator/backup` 產生一份完整副本，檔名帶著取用時刻（epoch 毫秒），
寫到 `HYROX_BACKUP_DIR`（出貨預設 `/var/lib/hyrox/backups`，就在 systemd 的 StateDirectory 裡）。

* **為什麼是 `VACUUM INTO`**：這是 SQLite 官方支援的線上備份，透過一般讀交易取得一致快照，
  含 `-wal` 裡已提交但還沒 checkpoint 的資料。`cp` 主檔會漏掉的正是那些。
* **為什麼是 API 而不是 shell 腳本**：主機是唯一被允許碰這個檔案的行程（ADR 0009 的單元檔
  就是這樣寫的）。維護腳本用 `curl` 要求，不自己開檔。
* **為什麼是寫入路徑**：它要帶 `x-operator-device` 並留下 `DATABASE_BACKUP` 稽核紀錄。
  一份包含場館全部歷史的副本離開了資料庫，「誰要求的」值得記下來，即使沒有任何紀錄被改動。
* **不覆蓋既有檔案**：`VACUUM INTO` 本來就拒絕，我們保留這個行為。會蓋掉昨晚那份的備份
  只是一份備份，不是歷史。

### 3. 一天備份兩次，保留十四天

**排程（`hyrox-backup.timer`）：12:00 與 21:00**，加上夜間視窗更新前的那一次。所以最壞情況
損失的是**半天**的課，不是一天。

為什麼敢在課程進行中備份：`VACUUM INTO` 透過一般讀交易讀取，而 WAL 模式下讀不擋寫。
一個場館的資料庫是幾 MB，複製是幾秒的事。

`Persistent=true`——和夜間視窗相反。夜間那個結尾是 `poweroff`，補跑會讓機器在早上開機後
幾秒鐘自己關掉；備份只是複製檔案，補跑是好事。

夜間維護（ADR 0009 §6）的順序：**先問可不可以停 → 備份 → 更新 → 驗證 → 關機**。

* 備份在更新**之前**，因為更新才是有風險的那一步。
* **備份失敗就不更新**，當晚到此為止。沒有備份的機器明天照樣能上課；沒有備份又更新失敗的
  機器可能就不行了。

**保留以天計，不以份數計**：`-mtime +14`。原本寫「保留 7 份」，一天兩次之後那就只剩三天半
歷史——排程一改，份數就會安靜地縮短保存期間。天數不會。

兩個呼叫者（排程與夜間）跑的是**同一支腳本** `packaging/bin/backup`，所以「什麼叫一次備份」
和「保留多久」各只有一份實作。備份的用途寫進稽核的 reason 欄（`scheduled` / `pre-update`），
早上要找檔案時分得出來。

### 4. 離開這台機器的副本：一支 USB 隨身碟

備份和資料庫在同一顆硬碟上時，備份幾次都擋不住硬碟本身壞掉。所以備份完成後可以再複製一份
到 USB 隨身碟：

* 隨身碟格式化成 exFAT 或 ext4，標籤 `HYROXBACKUP`；`media-hyroxbackup.mount` 以 `nofail`
  掛載它，**沒有任何東西等它**——拔掉隨身碟的場館照樣要能開機上課。
* 在 `/etc/hyrox/hub.env` 設 `HYROX_BACKUP_MIRROR=/media/hyroxbackup` 才會啟用。預設是關的：
  沒拿到隨身碟的場館不該每天看到一個失敗的 unit。
* 複製的是**備份檔**而不是資料庫本身。備份檔是一份已經完成的快照，所以這裡用 `cp` 是對的，
  而對 `hyrox.db` 用 `cp` 是錯的。
* **一定要確認它真的掛載了**（`mountpoint -q`）。掛載點沒掛就往裡面寫，會把系統碟寫滿，
  而且看起來一切正常——直到有人需要那份備份為止。這是這整段唯一真正難的地方。

**三種結果分開處理**，因為夜間視窗必須分得出來：

| exit | 意思 | 夜間視窗的反應 |
| --- | --- | --- |
| 0 | 備份完成（有設定就也鏡射了） | 繼續更新 |
| 1 | **完全沒有備份**——主機沒回應 | 今晚不更新 |
| 2 | 備份好了，但沒有異地副本 | 記一行 log，**繼續更新** |

隨身碟不見不該讓場館好幾週收不到安全更新；沒有備份則必須擋下更新。排程那支 unit 仍然會
因為 exit 2 變紅，所以早上看得到「該把隨身碟插回去了」。

### 5. 沒有做的事
* **往場館外送。** 送到雲端需要一個我們還沒有的決定：送到哪、誰持有、個資怎麼算。
  USB 隨身碟解決的是「硬碟壞掉」，不是「機器被偷」或「場館失火」。
* **定期背景檢查。** 只在開機時檢查。一台連續開機數週的機器不會自己發現靜默損壞。
  出貨形態每晚都會關機（ADR 0009），所以開機檢查實際上就是每日檢查——這個推論成立的前提是
  夜間關機真的在跑。
* **自動還原。** 主機不會自己拿備份蓋掉壞檔。那是人在早上做的決定，因為它會丟掉損壞之後的資料。

## Consequences

* 開機多了一次全頁掃描。空資料庫是毫秒級；一個賽季的資料庫仍在毫秒到低百毫秒之間。
* 夜間維護多一個失敗模式（備份失敗 → 今晚不更新）。這是刻意的取捨。
* 一天兩次、保留十四天，約 28 份副本。以一個場館的資料庫大小（數 MB）計，是幾百 MB，
  在出貨機器上不成問題；資料庫大到會擠爆時，先改的應該是保留天數。
* `HubStore` 多了一個 `backup_to` port，兩個假 store 都實作了。
* 壞檔時機器會停在「服務沒起來」的狀態，早上有人要處理。這比「服務在跑但資料是壞的」好，
  也比 restart loop 好。

## 驗證

* `crates/storage/tests/integrity.rs`：健康檔通過檢查；**真的把一個檔案寫爛**之後開檔被拒；
  執行中備份可獨立開啟且完整；不覆蓋既有備份。
* `crates/api/tests/lifecycle.rs`：備份端點回報路徑、檔名帶時刻、留下稽核紀錄、缺裝置名稱被拒。
* 備份腳本實跑：連續兩次產生兩份、稽核分得出用途、20 天前的檔案被輪替掉、主機不在時
  以 exit 1 失敗（紅的 unit），夜間維護因此不更新。
* 鏡射三種狀態實跑：沒設定 → exit 0；設了但目標沒掛載 → exit 2 且**本機備份仍然產生**；
  目標在 → 兩邊各一份。夜間視窗對 exit 2 記一行繼續、對 exit 1 停止更新。
* 實機走過一次完整循環：備份 → 把主檔寫爛 → 開機被拒（exit 78，印出還原指示）→
  用備份覆蓋 → 開機恢復原本的課程。
