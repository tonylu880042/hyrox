# ADR 0013 — 系統設定頁與電源控制

**Status:** accepted, 2026-09-02
**Extends:** ADR 0001（介面操作規則）、ADR 0009（出貨形態）
**Closes:** roadmap M6 的「異常清單與 reader 設定介面仍未做」

## Context

場館裝機時要把牆上每一支天線對應到站點。在這之前，唯一的方法是有人把 ESP32 的 MAC 抄下來、
手打進 `POST /api/operator/readers`。抄錯一個字元，那支讀卡機的每一次刷卡都會變成
`UNKNOWN_READER` 例外，而且要到課上到一半才發現。

同時，場館人員沒有辦法自己關機或重開——`/live` 卡住就只能找人走到機器前面。

## Decision

### 1. 待設定的讀卡機是**推導**出來的，不是打字打出來的

`GET /api/operator/readers/unregistered` 回傳「主機聽過但認不得」的 `(device_id, reader_id)`，
最近刷過的排最前面。

推導自 `raw_events`——主機本來就把無法歸屬的刷卡存下來（CLAUDE.md 31），所以**拿手環碰一下
天線，它就出現在清單最上面**。裝機的流程變成：碰一下、指派站點、碰下一支。沒有人需要看 MAC。

指派用的是既有的 `register_reader` 用例，指派完就從清單消失，因為「未設定」是從註冊表推導的，
不是誰維護的一張名單。

站點欄位帶著今天課表的站點作為建議值：讀卡機的 station key 必須和課表**完全一致**，
否則它的刷卡會變成例外（ADR 0008）。

### 2. 電源控制放在網頁上，但「場上有課」永遠優先

`POST /api/operator/power`，三個動作：`POWEROFF`、`REBOOT`、`RESTART_SERVICE`。

畫面沒有登入（ADR 0001 D1：網路邊界就是安全邊界），而關機是這個介面上後果最大的動作，
所以它是唯一有自己護欄的：

* **課程進行中（`is_live`）拒絕關機與重開機器**，回 `409 CLASS_RUNNING`。問的是夜間維護
  問的同一個問題，所以兩邊不會各自解讀。
* **必須填理由**，並寫進稽核（`POWER_POWEROFF` / `POWER_REBOOT` / `POWER_RESTART_SERVICE`）。
  它會結束一個場館的晚上，這正是 CLAUDE.md 20 所說需要理由的動作。
* **稽核先寫，才動機器**。順序反過來的話，機器倒下的瞬間正好是那筆紀錄最重要而它還不存在的時候。
* **重啟主機服務不受課程限制**：它照設計就是可復原的——重放解讀日誌重建課程，期間發布的事件
  由 broker 佇列補上（CLAUDE.md 15、21）。這是唯一能讓卡住的畫面復原而不必走到機器前的辦法。

### 3. 用 polkit，不用 sudo

**這是在第一台實機上才發現的。** 一開始的實作是 `sudo -n systemctl`，並附一份只允許三個指令的
sudoers。從 shell 測完全正常，從主機呼叫一律 `permission denied`。

原因是服務單元的 `NoNewPrivileges=yes`——那個旗標存在的目的就是阻止服務透過 setuid 執行檔提權，
而 sudo 正是 setuid。為了三個按鈕把整個服務的強化拿掉，是很差的交換。

改成**不帶 sudo 直接呼叫 `systemctl`**：非特權的 `systemctl poweroff` 根本不是提權，它是對 logind
的一個 D-Bus 呼叫，`NoNewPrivileges` 不管它。允許什麼由一份 polkit 規則決定
（`packaging/etc/polkit-1/rules.d/50-hyrox-power.rules`）：使用者 `hyrox` 可以關機、重開機，
以及**只能**重啟 `hyrox-hub.service`——不能拿它去停 Mosquitto。

送出前先用 `systemctl --dry-run` 問一次：它走同一條授權路徑但什麼也不做，所以**規則沒裝的機器
會在畫面上得到錯誤，而不是一個按了沒反應的按鈕**。動作本身延遲兩秒執行，讓回應先送達平板——
在 handler 裡直接關機，操作者只會看到一個失敗的請求，不知道到底成功沒有。

### 4. 平台細節只有一個檔案知道

`api::Power` 是 port，`apps/hub-server/src/power.rs` 是唯一知道這台機器跑 systemd 的檔案
（CLAUDE.md 2）。開發機上預設是 `NoPower`，它**拒絕**而不是假裝成功——一個說「關機中」但什麼
也沒做的設定頁，比一個錯誤更糟。

### 5b. 讀取器可以手動新增，也可以移除

原本 ADR 0007 §7 寫「不做刪除」，理由是「已經透過它歸屬的事件怎麼辦」。查證後那個顧慮
**不成立**：`raw_events` 永遠留著每一筆刷卡的 device 與 reader（CLAUDE.md 19），而解讀事件
記的是**站點**不是讀取器。所以移除一份對應關係不會讓任何歷史變成孤兒，它只決定**下一筆**
刷卡的命運——變成 `UNKNOWN_READER` 例外，出現在異常清單，而不是無聲消失。

* **移除要填理由**，稽核記 `READER_REMOVE`，並在 `before` 欄留下「它原本代表什麼站點與模式」
  ——那是事後從地圖上再也重建不出來的東西。
* **手動新增**：讀取器還沒上牆、還沒刷過卡時，可以直接輸入裝置 MAC 與讀取器編號。碰一下自動
  出現仍然是主要路徑，手動是給裝機前先建好設定的人。

### 6. 場域自己的設定與 logo

設定頁的「大螢幕」分頁讓場館調整兩件事，兩者都存在資料庫（`venue_settings`、`venue_assets`），
不存在瀏覽器——**投影機是另一台機器**，存在平板的 localStorage 永遠到不了它。

* **換頁間隔**：3–120 秒，超出範圍拒絕。壞掉的存值退回預設而不是讓螢幕掛掉。
* **每頁人數**：**固定選項而非任意數字**——6（3×2）、12（4×3，預設）、20（5×4）、30（6×5）。
  每個都是完整的格子（欄×列＝人數），最後一列不會缺角；7 這種數字會留下殘缺的一列，
  而且沒有人決定過那些卡片該是什麼比例。版型清單只定義在 application 層，設定頁的選單和
  投影機的 grid 都讀同一份。
* **場館 logo**：頁首最左，排在系統名稱之前。這面牆屬於健身房，`uCareMedi.com` 是頁尾的
  供應商署名。沒有上傳就不顯示，不留空框。

logo 存在資料庫而不是磁碟：夜間備份（ADR 0012）本來就複製資料庫，所以還原後的機器牆上
仍然有那家店的標誌，而不是一個空角落。沒有目錄要建、沒有權限要設、沒有孤兒檔案要清。

**只收 PNG 與 JPEG，不收 SVG。** SVG 是一份可以夾帶程式碼的文件，而主機會用自己的來源把它
送給場館裡每一個畫面——包含操作介面。一個健身房的 logo 不值得那個風險。而且判斷依據是
**檔案開頭的位元組**，不是上傳時宣稱的類型：`logo.png` 是一個說法，magic bytes 才是事實。

### 7. 示範資料是一顆按鈕，而且預設不存在（2026-09-02 追加）

整合測試需要一整場課：課表、選手、讀取器、腳環，還有刷卡。以前這些是**開機就有**的——
`main.rs` 每次啟動都把 12 位假選手寫進資料庫，`--no-default-features` 只拿掉模擬刷卡，
拿不掉那份名單。所以一台交給場館的機器，第一次開機就有 12 個不存在的人。

改成：

* 開機只有一堂空的 DRAFT 課，沒有課表、沒有名單、沒有讀取器。場館自己從課表畫面開課。
* 示範資料變成 `POST /api/operator/demo`，設定頁上的一顆按鈕。
* **預設看不到那顆按鈕。** 要 `HYROX_DEMO=1` 才會有，`GET /api/settings` 的
  `demo_available` 就是畫面的依據——不是畫一顆會回 503 的按鈕。
* 護欄跟電源同一條：**課程進行中不能載入**。十二個憑空出現的選手混進別人的課，
  跟一個 bug 沒有分別。停止則隨時可以，因為需要開關的時候正是出事的時候。
* 載入走的是**平常那幾個 use case**（configure → 註冊讀取器 → 報到 → 綁腳環 → 開賽），
  所以示範資料造不出產品自己造不出的狀態；刷卡由模擬器經**真的 broker** 送出，
  走完整條 publish → commit → ACK → 判讀路徑。

順帶修掉的一件事：那個 12 倍速的開發時鐘原本**在場館機器上也是 12 倍速**。
現在沒開 `HYROX_DEMO` 就是實時。

## Consequences

* 裝機不再需要抄 MAC，也不再有「打錯一個字元、整晚的刷卡都是例外」這種失敗。
* 場館 Wi-Fi 上任何人都能按關機——擋在前面的只有「課程進行中」這道護欄和一個理由欄位。
  這是 D1 的信任模型延伸到電源上的結果；要更嚴格，門檻是加登入，而不是加確認對話框。
* 交出去的機器第一次開機是空的——這是對的，但也表示驗收要先建一堂課才看得到東西。
* polkit 規則是出貨機器的一部分。沒有它，設定頁的電源分頁會顯示錯誤——這是刻意的。

## 驗證

* `crates/application/tests/venue_setup.rs`：碰過的讀卡機出現在清單、已設定的不再出現、
  最近碰過的排最前、指派後從清單移除。
* `crates/api/tests/power.rs`：課程中拒絕關機、課程結束後允許、沒有理由被拒、缺裝置名稱被拒、
  不認識的動作被拒、重啟服務在課程中仍允許。
* `crates/api/tests/demo.rs`：沒有示範能力的主機回 503 且 `demo_available` 為 false、
  載入與停止各記一筆稽核、課程進行中載入被拒、停止不被拒、缺裝置名稱被拒。
* 實機（192.168.0.131，Ubuntu 24.04）：模擬一台沒設定過的讀卡機刷卡 → 出現在待設定清單 →
  從畫面指派 SKIERG/進站 → 從清單消失；課程進行中按關機得到 `CLASS_RUNNING`；
  重啟主機服務成功，日誌顯示 `resumed session ... with 13 athletes`，稽核有理由。
