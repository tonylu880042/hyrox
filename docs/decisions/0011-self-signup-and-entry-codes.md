# ADR 0011 — 自助報名與六碼報名編號

**Status:** accepted, 2026-09-01
**Extends:** ADR 0001 D1（操作者身分）、D3（腳環綁定）、ADR 0010（非會員參賽）

## Context

場館辦模擬賽時，來的人不一定是會員。ADR 0010 已經讓「健身管不認識的人」可以被放進名單，
但放進去的動作只有櫃檯做得到——一個人一個人問名字、一筆一筆打字。三十個人報到，
櫃檯就是瓶頸。

同時，這些人賽後要能查自己的成績。他們沒有帳號，也不會為了一場模擬賽去辦一個。

需求（2026-09-01）：

1. 非會員可以自己報名
2. 報名完成後拿到一個 QR，代表這個人
3. QR 用來在報到處跟 RFID 腳環配對
4. 同一個編號可以當作臨時會員編號，賽後查成績

## Decision

### 1. 六碼報名編號，而且它就是 athlete id

編號長這樣：`K7QD2M`。字母表是 Crockford base32 再拿掉 `U`——沒有 `I`、`L`、`O`，
因為在手機螢幕上一臂之遙，它們就是 `1`、`1`、`0`。解析時把人會打錯的字元對回去
（`O`→`0`、`I`/`L`→`1`），大小寫、空白、連字號都寬容。

**它不是另一個號碼，它就是 athlete id。** 走過的替代方案是「另外發一個查詢碼，對到內部
id」——那需要一張對應表、一個同步問題，以及「兩邊不一致時信哪個」的答案。一個值同時是
身分、QR 內容和查詢碼，就沒有不一致可言。

會員不發編號：他們有健身管的 member_id，那才是他們跨課程的身分（ADR 0010）。
一個人兩個號碼、而且沒有規則說哪個優先，是我們不要的。

產生編號的隨機性在 application 層，domain 只知道怎麼把一個數字變成六個字元。
domain 一旦伸手要亂數就不能重放了（CLAUDE.md 21、29）。

### 2. `POST /api/checkin/signup`：全站唯一不需要身分的寫入

D1 說每一筆寫入都要帶操作者的裝置名稱，沒帶就拒絕，因為「沒有署名的稽核紀錄比沒有紀錄
更糟」。自助報名沒有裝置可以署名——所以稽核紀錄寫的是 `SELF SIGN-UP`，那是事實，
不是借用某台平板的名字。

這條路徑被刻意做得很窄：

* **只收姓名。** 不收號碼布（印好的號碼是櫃檯發的，讓公眾自己挑會出現兩個 07），
  不收 member_id（未經驗證的路徑不該能宣稱自己是某個會員）。多送的欄位被忽略，不是報錯。
* **報名是惰性的。** 綁腳環仍然需要櫃檯的裝置名稱，所以在工作人員把腳環交出去之前，
  一筆自助報名不會影響任何計時。
* **它放在 `/api/checkin` 底下**，因為它做的事就是報到在做的事。放到別的路徑會讓
  ADR 0007 §5 的「寫入只存在兩個前綴」失效。

信任模型沒有改變：網路邊界仍然是部署層的事（D1）。場館 Wi-Fi 上的人可以報名，
就像他們本來就可以看大螢幕一樣。

### 3. QR 裡放六個字元，不放網址

報到處用的是條碼掃描槍——它在作業系統眼中是一個鍵盤。掃描等於「把內容打進游標所在的
輸入框」。如果 QR 裡是一串網址，掃描槍就會把網址打進搜尋框，完全沒用。

QR 由主機自己畫成 SVG（`qrcode` crate，不含影像編解碼），跟字型、圖示一樣從主機出，
不走 CDN——沒有網路的場館還是要能發出報名證。

### 4. 相機掃碼是備援，不是主要方案

`/checkin` 提供相機掃碼，用瀏覽器內建的 `BarcodeDetector`，不引入任何 JS 函式庫。

但它有一個我們解不掉的限制：**相機需要安全內容（HTTPS 或 localhost）**，而主機在場館
區網上是 http。所以平板上的相機掃碼在目前的出貨形態下不會動，畫面會直接說明並要求改用
掃描槍或手動輸入六碼。

要讓相機掃碼在場館可用，得先決定 TLS 怎麼做（自簽憑證要在每台平板上信任，或給機器一個
真實網域）。那是 ADR 0009 出貨形態的延伸決定，尚未做。

### 5. 選手只有一個頁面

`/signup` 同時是報名表、報名證和成績查詢。網址帶著編號（`/signup?code=K7QD2M`），
所以截圖、加書籤、關掉再開都能回到同一個地方——主機沒有帳號可以登入，選手的手機就是
唯一保存的地方。

成績只給自己那一列（`GET /api/entry/{code}`），不給整份排行榜：這是選手自己開的頁面，
拿著一個編號就能看到全場每個人的分段，等於把名單公開了。整份排行榜在 `/leaderboard`，
那是場館決定要不要投影出來的東西。

## Consequences

* 櫃檯不再是報名的瓶頸；它只做「把腳環交給誰」這件需要人的事。
* 名單上會出現沒有人核對過的名字。這是模擬賽本來就有的狀況——號碼布仍然是櫃檯發的，
  沒領到腳環的人不會有成績。
* 編號可以被猜（32^6 ≈ 十億分之一，一次一猜）。猜中的後果是看到某個人的名字與分段。
  在一場模擬賽的風險等級上這是可接受的；如果哪天不可接受，門檻是加上速率限制，
  而不是加上帳號。
* 相機掃碼在 http 下不可用，已寫進畫面文案與 `docs/open-issues.md`。

## 順帶修掉的一個復原缺陷

實作時發現：**復原既有課程時沒有把號碼布讀回來**（`resume_or_start` 的 resume 分支
從未呼叫 `note_bib`）。重開機之後，下一位報名者會拿到號碼布 1，而 1 已經有人穿——
資料庫以 UNIQUE 拒絕寫入，選手在櫃檯被擋下來，原因是一次沒人看到的重啟。

號碼布是儲存的事實而不是事件，所以不會被重放帶回來，必須明確讀回。已修，並有回歸測試
（`crates/application/tests/recovery.rs::a_resumed_session_gets_the_bibs_it_already_handed_out`）。
