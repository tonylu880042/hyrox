# 健身管整合模式草案

**狀態：已決策（使用者，2026-09-08）。** 對外規格見
[gym-integration-spec.md](gym-integration-spec.md)。這份文件保留下來，是為了記住為什麼這樣選。

| | 決定 |
| --- | --- |
| D1 | **A** — QR 帶明碼 `member_id`；健身管提供一支 API 供查詢暱稱、性別、年齡、頭像 |
| D2 | **A** — 呼叫健身管的 API 取得，成功結果在本機快取（斷網仍要能報到） |
| D3 | **A** — 我方發動，課後呼叫健身管的雲端 API |
| D4 | **A** — 總結 ＋ 每站分段 |
| D5 | **A** — 每次重送最後的完整結果（upsert）。**上課過程中不同步**，只在課程結束或該會員離場時送 |

採用**模式 2**，分兩階段交付。

範圍：**從報到那一刻，到課程結束後把運動紀錄送回健身管**。

現況：`application::MemberDirectory` port 已存在，唯一實作是 `UnconfiguredDirectory`
（一律回報未設定）。回傳紀錄那一半**完全沒有程式碼**，工作區也還沒有任何 HTTP client 依賴。
所以下面的選擇會直接決定要蓋多少東西。

---

## 0. 兩個不能被整合推翻的前提

1. **場館沒網路也要能上課**（CLAUDE.md 31）。任何「報到時必須打得到健身管」的設計，
   都必須附一條降級路徑，否則網路一斷全場停擺。
2. **場館主機是紀錄的產生者與第一手保存者**。健身管收到的是複本，不是計時權威。
   成績以場館端為準，修正也從場館端發起。

另外一個順帶的好處值得先講：`docs/open-issues.md` 有一條未解議題是
「個人運動紀錄要放在雲端，不放在場館」。如果健身管願意收運動紀錄，
**這條議題就被這次整合解掉了** — 健身管就是那個雲端，不必再自己蓋一套。

---

## 1. 五個決策點

每個點的建議放在第一列。

### D1 — QR 裡放什麼（報到識別）

| | 做法 | 代價 |
| --- | --- | --- |
| **A ✅** | QR 直接帶 `member_id`（明碼或簡單編碼） | 可被抄寫、轉傳。但 hub 本來就不擋會籍（已定案），冒用的收穫只是「用別人的名字上課」，成本低於防偽的複雜度 |
| B | QR 帶健身管簽發的短效 token，hub 呼叫健身管換 `member_id` | 防偽。但報到當下必須連得上健身管，違反前提 1，得再設計降級 |
| C | QR 帶簽章過的 `member_id` + 姓名 | 離線可驗、可離線報到。需要雙方交換金鑰與簽章格式 |

補充：現場已支援掃描槍（相機掃碼受 HTTPS 限制，見 open-issues）。
掃描槍等同鍵盤輸入，所以 QR 內容**必須是純文字、不要是 URL**。

### D2 — 會員資料怎麼拿

| | 做法 | 代價 |
| --- | --- | --- |
| **A ✅** | 現場逐筆查詢 + 成功結果快取 N 天（預設 7） | 常見情況零延遲、斷網時老會員照樣有名字有照片。hub 存的是查過的人，不是整份會員庫 |
| B | 純逐筆查詢，不快取 | 最乾淨，但斷網＝新舊會員全部退化成現場報名 |
| C | 每日全量同步一份精簡名冊 | 離線最完整，但等於在場館複製了一份會員庫（CLAUDE.md 7.1 明講不要） |

斷網或查不到時的行為**不變**：照樣可以報到，走現有的現場報名路徑，只是沒有照片與年齡。
會籍狀態一律不擋人（2026-08-27 已定案）。

hub 要的欄位（已在 `domain::MemberRef` 定型，多的不要）：

```
member_id, display_name, status,
gender?, age?, photo_url?, height_cm?, weight_kg?
```

### D3 — 運動紀錄由誰發動

| | 做法 | 代價 |
| --- | --- | --- |
| **A ✅** | hub 主動推（push）給健身管 | 場館主機在區網、多半在 NAT 後面，對外連線只能由它發起。要在 hub 蓋一個送件佇列（outbox）與重試 |
| B | 健身管定時來抓（pull） | hub 端最省事（幾乎只是多一個 `?since=` 的查詢），但需要對方連得進場館內網 — 現實上做不到，除非另外拉 VPN / 固定位址 |
| C | 場館 → 自建雲端 → 健身管 | 多一段基礎建設要養。除非未來有多場館彙總需求，否則現在不划算 |

實務上 **A 是唯一不需要動網路架構的做法**。

### D4 — 送什麼粒度

| | 做法 | 代價 |
| --- | --- | --- |
| **A ✅** | 每人每堂課一筆總結 **＋** 每站分段（現成的 `ResultRow` + `SplitRow`） | 分段是這套系統對會員唯一有價值的東西（每站用時、轉換時間）。不送等於只送一個沒有意義的總時間 |
| B | 只送總結 | 對方最好接，但會員在健身管上看到的東西很單薄 |
| C | 連原始刷卡事件一起送 | 不建議。那是場館的內部證據與稽核依據，送出去只會製造第二個真相 |

**不上傳現場報名（walk-in）的人**：他們沒有 `member_id`，健身管也不認識他們，
上傳等於把非會員個資推給第三方系統。他們的成績留在場館，用六碼查詢頁看。

### D5 — 修正怎麼同步

場館端作廢一筆解讀會重算成績（ADR 0001 D4）。已經送出去的成績必須能更新。

| | 做法 | 代價 |
| --- | --- | --- |
| **A ✅** | 冪等鍵 `venue_id + session_id + athlete_id`，健身管端「同鍵覆寫」（upsert） | hub 不必發明撤回語意，重算完重送一次就好。重送＝真相。要求對方端點是 PUT/upsert 而非 append |
| B | 送修正單（delta），對方自己套用 | 雙方都要維護狀態機，錯一次就永久對不上 |
| C | 送出後不可改 | 最省事，但場館一改成績兩邊就永久不一致 |

再加一個 `revision` 整數與 `recorded_at`，讓對方能辨識新舊、丟棄過期的重送。

## 2. 三種整合模式（打包後的選擇）

### 模式 1 — 只認人

只做 D1 + D2。健身管提供一支查詢會員的 API，運動紀錄**不回傳**，
留在場館，用結果頁 / QR 給會員自己看。

- 對方工作量：一支唯讀 API。
- 我方工作量：`MemberDirectory` 的真實實作 + 快取。約 1–2 天。
- 適合：對方短期內開不了寫入 API，但想先讓報到有照片有姓名。

### 模式 2 — 認人 ＋ 單向回傳 ✅ 建議

模式 1 加上 D3-A / D4-A / D5-A：課程結束後，hub 把每位會員的成績與分段推回健身管。

- 對方工作量：一支唯讀查詢 API ＋ 一支 upsert 寫入 API ＋ 一組場館憑證。
- 我方工作量：上面那些，加一張 outbox 表、一個背景重送、一個送件狀態畫面。約 4–6 天。
- 換到的東西：會員在健身管 App 裡看得到自己每一次的 HYROX 紀錄。
  順帶把「運動紀錄放雲端」那條未解議題解掉。

### 模式 3 — 雙向：課表與報名也整合

模式 2 再加上健身管把「今天有哪幾堂課、誰報名了」推給場館，開課即有名單。

- 對方工作量：再加一支課程／報名 API，而且要處理現場臨時加人、換課、退課。
- 我方工作量：明顯更大，而且會引進**衝突解決**（兩邊都能改名單），目前完全沒有。
- 建議：**先不要**。等模式 2 上線跑過幾個月，確定名單同步真的是痛點再說。

---

## 3. 建議

**選模式 2，但分兩階段交付**：先上模式 1（報到認人），確認雙方 API 與憑證流程沒問題，
再接回傳。這樣第一階段就算對方寫入 API 延後，場館也已經拿到看得見的價值。

---

## 4. 決定之後，要跟對方拿的東西

寫對外整合文件時，這幾項必須是對方給的答案，不能由我方假設：

1. 會員查詢的 endpoint、認證方式（API key？OAuth？場館層級還是使用者層級）
2. QR 碼目前實際的內容格式 — 現場已經在用的那一種是什麼
3. 運動紀錄寫入的 endpoint，以及**是不是 upsert**（D5 的成敗在這裡）
4. 對方要不要收分段資料，欄位怎麼命名
5. 速率限制、逾時、錯誤碼；以及會員不存在時回什麼
6. 測試環境（沒有測試環境就無法做 TDD，這會直接影響交付時程）
