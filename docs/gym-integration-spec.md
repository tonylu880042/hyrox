# HYROX 場館主機 ↔ 健身管 整合規格（討論版 v0.1）

日期：2026-09-08　　狀態：**待雙方確認**

這份文件提出兩支 API 的規格草案，供雙方討論。欄位名稱、路徑與認證方式都可以改；
**不能改的是流程與語意**，那部分在第 1 節與第 6 節說明理由。

---

## 1. 整合範圍與流程

場館端有一台本機主機（以下稱「場館主機」），負責 RFID 讀取、計時、成績計算。
會員的完整檔案留在健身管，場館主機不複製會員資料庫。

```
  會員出示 QR（內含 member_id）
        │
        ▼
  [報到] 場館主機 ──── GET 會員資料 ────▶ 健身管       ← API 1
        │            ◀─ 暱稱/性別/年齡/頭像 ─┘
        ▼
  [上課] 刷卡、計時、分段計算           （全程不與健身管通訊）
        │
        ▼
  [結束] 課程結束，或該會員離場
        │
        └────── PUT 運動紀錄 ─────────▶ 健身管         ← API 2
```

兩個貫穿全文的前提：

1. **場館主機必須在沒有網路時照常運作。** 健身管不可用時，報到、計時、成績全部照常，
   只是少了頭像與年齡，紀錄留在佇列裡等網路恢復。整合不得成為上課的單點故障。
2. **場館主機是成績的產生者，健身管收到的是複本。** 成績以場館端為準，
   修正也從場館端發起（見第 6 節）。

## 2. 認證（待確認）

提案：**場館層級**的長期憑證，由健身管核發給每一個場館。

```
Authorization: Bearer <venue_token>
```

場館主機是一台放在場館裡的機器，沒有「登入中的使用者」，所以不適用使用者層級的
OAuth flow。憑證存在場館主機的設定檔，不進版本控制。

需要健身管確認：憑證形式、有效期、輪替方式，以及是否需要額外的 `venue_id` 欄位識別場館。

## 3. API 1 — 會員查詢（健身管提供）

QR 碼內容為 **純文字的 `member_id`**（不是 URL）。場館報到使用條碼掃描槍，
掃描槍等同鍵盤輸入，掃到 URL 會被打進搜尋列而不是欄位。

### 請求

```
GET  {base_url}/members/{member_id}
Authorization: Bearer <venue_token>
```

### 回應 `200`

```json
{
  "member_id": "M0012345",
  "display_name": "小明",
  "status": "ACTIVE",
  "gender": "MALE",
  "age": 34,
  "photo_url": "https://cdn.example.com/avatar/M0012345.jpg",
  "height_cm": 175,
  "weight_kg": 68
}
```

| 欄位 | 必填 | 說明 |
| --- | --- | --- |
| `member_id` | ✔ | 與請求相同 |
| `display_name` | ✔ | 暱稱，顯示在報到畫面與大螢幕 |
| `status` | ✔ | `ACTIVE` / `SUSPENDED` / `EXPIRED`。**僅供顯示**，場館端不用它擋人上課 |
| `gender` | | `FEMALE` / `MALE` / `OTHER` |
| `age` | | 整數歲。場館端存下的是查詢當下的歲數，不是生日 |
| `photo_url` | | 頭像位址，見下方註記 |
| `height_cm` | | 整數公分 |
| `weight_kg` | | 整數公斤 |

未知的 `status` 值場館端會顯示為 `UNKNOWN`，不會擅自視為有效會籍。

**關於 `photo_url`：** 場館主機可能沒有對外網路，抓不到圖時就不顯示頭像，不影響報到。
請確認圖片是否可公開存取（或同樣吃 Bearer token），並希望提供**長邊 ≤ 512px、
≤ 100KB** 的縮圖版本 — 大圖在場館的無線網路下會拖慢報到。

### 其他回應

| 狀態碼 | 場館端行為 |
| --- | --- |
| `404` | 查無此會員。**仍然讓人報到**，走現場報名流程，只是沒有會員資料 |
| `401` / `403` | 憑證問題。記錄並在設定畫面顯示警示，不擋上課 |
| `5xx` / 逾時 | 視同查不到，照常報到 |

場館端逾時設定：**2 秒**。報到隊伍不能為了一張頭像卡住。

### 快取

查詢成功的結果，場館端會在本機保留一段時間（預設 7 天）以支援斷網報到。
保留的僅有上表欄位，不是會員資料庫的複本。如果健身管對此有政策上的意見請提出。

## 4. API 2 — 運動紀錄回傳（健身管提供）

### 何時送

- **課程結束時**：全班一次送出。
- **該會員離場時**：只送這一位。

上課過程中**不同步**。過程中的中間狀態沒有意義，且會對健身管造成無謂的流量。

### 請求

```
PUT  {base_url}/workout-records/{venue_id}/{session_id}/{member_id}
Authorization: Bearer <venue_token>
Content-Type: application/json
```

**必須是 upsert（同鍵覆寫），不是 append。** 理由見第 6 節。

```json
{
  "venue_id": "hyrox-taipei-01",
  "session_id": "2026-09-08-1900-group",
  "member_id": "M0012345",
  "revision": 1,
  "recorded_at": 1787738400000,

  "session": {
    "name": "HYROX 團體課 19:00",
    "mode": "TRAINING",
    "finish_policy": "CLASS_DURATION",
    "started_at": 1787734800000,
    "ended_at": 1787738400000
  },

  "result": {
    "status": "FINISHED",
    "started_at": 1787734821382,
    "finished_at": 1787738012500,
    "elapsed_ms": 3191118,
    "stations_completed": 6,
    "place": 3
  },

  "splits": [
    {
      "sequence": 1,
      "station": "RUN",
      "entered_at": 1787734821382,
      "exited_at": 1787735061382,
      "work_ms": 240000,
      "transition_ms": null
    },
    {
      "sequence": 2,
      "station": "SKIERG",
      "entered_at": 1787735077682,
      "exited_at": 1787735322682,
      "work_ms": 245000,
      "transition_ms": 16300
    }
  ]
}
```

### 欄位說明

所有時間戳為 **UTC epoch 毫秒**（整數）。所有時間長度為毫秒（整數）。

**頂層**

| 欄位 | 說明 |
| --- | --- |
| `venue_id` | 場館識別碼，由健身管核發 |
| `session_id` | 該堂課的識別碼，場館端產生，全場館唯一 |
| `member_id` | 會員編號 |
| `revision` | 從 1 起算。**同一組鍵重送時遞增**；收到比已存較小的 revision 應忽略 |
| `recorded_at` | 這一版產生的時刻 |

**`session`**

| 欄位 | 說明 |
| --- | --- |
| `name` | 課程名稱，顯示用 |
| `mode` | `TRAINING`（團課／訓練）或 `COMPETITION`（競賽） |
| `finish_policy` | `CLASS_DURATION`（時間到就結束）／ `COURSE_COMPLETE`（跑完全程）／ `COACH_DECIDES` ／ `NOT_CONFIGURED`。決定 `place` 有沒有意義 |
| `started_at` / `ended_at` | 課程起訖 |

**`result`**

| 欄位 | 說明 |
| --- | --- |
| `status` | `FINISHED` / `ACTIVE` / `READY`。時間到還沒跑完的人是 `ACTIVE`，**這是團課的正常結果，不是錯誤** |
| `started_at` | 該會員第一次有效刷卡的時刻。`null` 表示全程沒刷到 |
| `finished_at` | 完成時刻；未完成為 `null` |
| `elapsed_ms` | 總用時 |
| `stations_completed` | **完成**的站數（進去還沒出來的不算） |
| `place` | 名次，從 1 起算。`null` 表示這堂課沒有名次可言（例如時間到才結束的團課，每個人做的量不同，排名無意義） |

**`splits`** — 每站一筆，依實際發生順序

| 欄位 | 說明 |
| --- | --- |
| `sequence` | 第幾站，從 1 起算 |
| `station` | 站點名稱，例如 `RUN`、`SKIERG`、`SLED_PUSH`、`WALL_BALLS` |
| `entered_at` / `exited_at` | 進出時刻。`exited_at` 為 `null` 表示課程結束時人還在站內，此時 `work_ms` 也是 `null` — 沒有讀取器回報他離開，場館端不會捏造一個時間 |
| `work_ms` | 該站用時 |
| `transition_ms` | 與前一站之間的轉換時間（HYROX 的 ROX Zone）。第一站為 `null` |

### 回應

| 狀態碼 | 場館端行為 |
| --- | --- |
| `200` / `204` | 成功，從送件佇列移除 |
| `409` | 視為「已有較新版本」，不再重送 |
| 其他 `4xx` | **不重試**。標記為失敗並在場館設定畫面顯示，由人處理 |
| `5xx` / 逾時 | 重試（指數退避，最長間隔 1 小時，最多重試 24 小時；主機重開機後續傳） |

請求逾時：10 秒。

## 5. 不會上傳的資料

| | 為什麼 |
| --- | --- |
| **現場報名者（非會員）** | 他們沒有 `member_id`，健身管也不認識他們。上傳等於把非會員的個資推給第三方系統。他們的成績留在場館，用查詢碼自己看 |
| **原始 RFID 刷卡事件** | 那是場館的內部證據與稽核依據。送出去只會製造第二個真相，且無法在健身管端重算 |
| **手環／標籤編號** | 手環每堂課重新綁定，對健身管沒有意義 |

---

## 6. 為什麼寫入端點必須是 upsert

場館端允許教練事後修正誤判（漏刷、誤刷、站點判錯），修正後成績會**整筆重算**。
已經送出去的成績因此必須能被更新。

- **upsert（本案採用）**：場館端重算完，用同一組 `venue_id + session_id + member_id`
  再送一次，`revision` 加一。最後送到的那一版就是真相。場館端不需要發明「撤回」語意，
  健身管端不需要維護狀態機。
- **append-only**：健身管端會累積同一個人同一堂課的多筆紀錄，得自己決定哪筆算數。
- **送修正單（delta）**：雙方都要維護狀態機，中間漏掉任何一筆就永久對不上。

實務上修正很少發生，但它一定會發生；而發生時兩邊成績不一致，是會員會直接看到的問題。

---

## 7. 待健身管確認的事項

1. **會員查詢**：實際的 endpoint、路徑與認證方式；上表欄位的實際命名
2. **QR 碼**：目前會員 App 的 QR 內容實際是什麼格式？是否就是純文字 `member_id`？
3. **頭像**：`photo_url` 是否可公開存取？能否提供 ≤ 100KB 的縮圖？
4. **寫入端點**：是否能提供 upsert 語意（第 6 節）？
5. **分段資料**：健身管是否要收 `splits`？會員 App 是否有畫面呈現？
6. **速率限制與逾時**：查詢與寫入各自的限制；一堂課結束時場館端會在短時間內送出
   十幾到數十筆紀錄，需要確認是否需要放慢或改為批次
7. **測試環境**：是否有可供串接測試的環境與測試帳號。**這一項會直接影響交付時程**

## 8. 分階段交付提案

| 階段 | 內容 | 前置條件 |
| --- | --- | --- |
| 一 | 報到查詢會員（API 1） | 健身管提供查詢 API 與測試環境 |
| 二 | 課後回傳運動紀錄（API 2） | 健身管提供 upsert 寫入 API |

先做階段一，可以在寫入 API 還沒好之前，就讓場館的報到畫面有正確的暱稱與頭像。
